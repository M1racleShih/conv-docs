调研报告：手机端灵活查看 workspace 文档

herdr 工作流缺少的一环：在不扩大 PC 暴露面的前提下，随时在手机上只读查看某个 workspace 的 Markdown 与 HTML 文档。本页记录需求、调研过程、候选方案对比和最终选型。

调研日期：2026-10-05 · 数据来源：GitHub API、Cloudflare 官方文档、OWASP Cheat Sheet（文末列证据）

一、需求清单

编号需求说明
R1 明确授权只有显式授权的目录才能在手机上看到防止隧道变成「整个 PC 文件系统可读」的后门
R2 只读手机端不提供编辑能力改文档继续走 agent（herdr），手机只消费
R3 渲染支持 Markdown 和 HTML 渲染，至少 HTML文档要「能看」，不是下载源码
R4 认证必须持 token 访问，不能匿名公网 URL 不等于公开内容
R5 安全在不影响现有使用的前提下尽可能安全现有 herdr-remote 控制通道（Cloudflare + 域名 + relay）零改动

使用场景的隐含约束：手机随时打开（无需先构建站点）、无需账号体系（单人使用）、网络环境可能访问公共 CDN 不稳定（静态资源应本地内置）。

二、调研方法

先找现成轮子，找不到或不匹配再造。对每个候选检查三件事：

  • 能力匹配——是否原生满足 R1–R5，还是需要魔改；
  • 受欢迎程度——GitHub star 数（截至 2026-10-05 由 GitHub API 读取）；
  • 活跃程度——最近一次提交时间、仓库是否已归档（归档即不可依赖）。

三、候选方案对比

方案 A：扩展现有 herdr-remote relay

在 relay 上加 /docs 只读接口和手机页面，复用现有隧道、token 和审计日志。部署最省事，但文档功能直接扩大了 agent 控制通道的攻击面——文档解析、路径处理的任何漏洞都能摸到发号施令的 WebSocket 接口。与 R5 的「不影响现有使用」相悖，放弃。

方案 B：现成文件服务器

项目Star最近提交能力匹配
sigoden/dufs 10,8352026-06 功能全（搜索、上传、WebDAV），默认只读可用；但无 Markdown 渲染，认证是 Basic/Digest 而非 Bearer token，且单实例单根目录，无法按需发布多个 workspace。写入能力（上传/删除/WebDAV）即使不用，也要逐一关闭才能放心。
svenstaro/miniserve 7,8892026-10 纯只读静态服务，稳定活跃；但无 Markdown 渲染，认证是 HTTP Basic（每次弹窗输密码，手机体验差），同样单根目录。
filebrowser/filebrowser 35,927已归档 仓库已归档 功能上是带编辑器的网盘，违反 R2，且归档后无维护，直接排除。

结论：文件服务器解决「把文件递出去」，不解决「渲染」和「按需发布」；要么放弃 R3，要么给它们套一层渲染层——套完之后仍然要自己写授权模型，不如直接组合渲染轮子自建网关。

方案 C：现成文档站工具

项目Star最近提交能力匹配
docsifyjs/docsify 31,5442026-10 客户端 Markdown 文档站，渲染效果好；但模型是「一个站点一套 index.html + 侧边栏」，不支持多根目录按需发布，也无认证。想看任意 workspace 得为每个 workspace 起一个站点并同步文件，与「随时查看」冲突。
squidfunk/mkdocs-material 27,5402026-10 渲染一流的静态文档站，但要先构建：agent 刚写的文档要重新跑构建才能看，灵活性不满足使用场景。适合「发布态」文档，不适合「工作态」文档。
dullage/flatnotes 3,2372026-08 自托管 Markdown 笔记，自带编辑器（违反 R2），单库模型，不支持浏览多个 workspace 目录。

方案 D：自建轻量只读网关 + 成熟渲染栈（选定）

自己写的部分只保留「必要的胶水」：显式发布授权、token 认证、路径沙箱、只读 API。渲染交给久经考验的开源轮子，直接内置（vendor）到仓库：

轮子Star最近提交License用途
markedjs/marked v18.0.14 37,2232026-10MIT Markdown → HTML，浏览器端渲染，零依赖
cure53/DOMPurify 3.4.16 17,4392026-10Apache-2.0 HTML/XSS 清洗。OWASP XSS 防护备忘单明确推荐对用户自产 HTML 做 sanitization 并点名 DOMPurify
highlightjs/highlight.js 11.12.0 25,0032026-09BSD-3-Clause 代码块语法高亮

服务端选择 Python 3 标准库实现 HTTP 服务（http.server），不引入任何运行时第三方依赖——目标机器（跑 herdr 的 PC）已有 Python，安装零摩擦；HTTP 层需求简单（只读 GET + 静态资源），标准库足够，也少一条供应链。

选型结论：方案 D。选它是因为「按需发布的多根目录 + Bearer token + 只读 + 渲染」这个组合没有现成产品同时满足，只能自建网关；而真正有风险、有难度的部分——Markdown 解析、XSS 清洗、语法高亮——全部交给 star 数 1.7 万～3.7 万、仍在活跃维护的成熟库。

四、基础设施侧的确认

  • Cloudflare Tunnel 一隧多站：本地管理的 tunnel 通过配置文件的 ingress 规则把不同 hostname 路由到不同本地服务。新增 docs.域名 → 127.0.0.1:8380 不需要动 relay 的规则，现有控制通道零改动（来源：Cloudflare 文档「Published applications / configuration file」）。
  • 免费额度：发布应用本身不需要付费计划；Cloudflare Access（可选的第二层防护）才需要 Access 席位。
  • HTTPS：隧道边缘天然 TLS，服务本体只需绑定 127.0.0.1。

六、已知取舍

  • 不做全库搜索：手机端「查看」为主，搜索后续按需加（客户端过滤目录内文件名已覆盖基本场景）。
  • 不做多用户：单人使用，一个 token；吊销即全局吊销，模型简单反而安全。
  • HTML 完整脚本模式受限：默认渲染是清洗后的安全模式；带脚本的交互式 HTML 走沙箱 iframe（详见方案设计），脚本能力受浏览器沙箱约束，这是为保护 token 必须付的代价。
  • 静态资源本地内置（vendor）而非 CDN：多占约 200 KB 体积，换来弱网/无 CDN 环境下手机端可用，且没有 CDN 侧的供应链风险。
