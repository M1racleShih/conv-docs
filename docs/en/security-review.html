Security Review

A STRIDE-based review of the conv-docs 0.1.0 code. Scope: HTTP surface, authentication, path handling, configuration and credential storage, audit logging. Method: read the actual code; every finding names its location, exploit scenario and disposition.

Reviewed 2026-10-05 · Method: STRIDE (Spoofing / Tampering / Repudiation / Information disclosure / Denial of service / Elevation of privilege)

Findings and dispositions

Four actionable findings (1 medium, 3 low) — all fixed or hardened; five residual risks accepted and recorded.

M1 · The full-mode iframe cannot carry credentials; the sandbox page never actually loaded medium · fixed

CategoryInformation disclosure / design deviation (Spoofing × availability)
Locationsrc/conv_docs/server.py, route /api/v1/rawhtml (previously required Bearer auth)
ScenarioA sandboxed iframe is a browser navigation and cannot send an Authorization header, so the request always got 401 — "full mode" was rendering a JSON error page. A wrong fix (long-lived token in the URL) would have leaked credentials into browser history and logs.
DispositionThe one-shot ticket is now the sole credential for this endpoint: only an authenticated caller can obtain one (html-ticket still requires Bearer), tickets expire in 30 seconds, are single-use and file-bound; invalid tickets count toward rate limiting and the audit log. The browser smoke test asserts at network level that the sandboxed request really returns an HTTP 200 document. Tickets cannot be brute-forced (192-bit random).

L1 · The source key is spoofable (rate-limit bypass when exposed directly) low · hardened

CategorySpoofing
Locationsrc/conv_docs/server.py, client_key()
ScenarioIf the service were misconfigured as directly public (--host 0.0.0.0), an attacker could rotate fake Cf-Connecting-Ip values to dodge per-source rate limiting and pollute the audit log.
DispositionThe trust boundary is loopback + tunnel (the deployment guide forbids direct exposure; behind the tunnel the header is set by the Cloudflare edge and cannot be spoofed). Hardened: source keys are truncated to 64 characters to keep logs and the limiter table clean. Residual: a 256-bit token cannot be brute-forced anyway, so the limiter is defence in depth; Cloudflare Access can add another layer (deployment guide §6).

L2 · Slow connections could pin worker threads low · fixed

CategoryDenial of service
Locationsrc/conv_docs/server.py, DocgateHandler
ScenarioSlowloris-style clients holding sockets without completing a request.
DispositionPer-connection socket timeout of 30 s; URL length cap 4096; request bodies never read; worker threads are daemons.

L3 · Large files were read into memory whole low · fixed

CategoryDenial of service
Locationsrc/conv_docs/server.py, _api_raw() (previously fh.read())
ScenarioA multi-gigabyte PDF/image in a published directory would be loaded into memory per request; concurrent requests could exhaust RAM.
DispositionStreamed in 64 KB chunks with Content-Length taken from the file size.

Accepted residual risks

  • Published content visibility: non-hidden sensitive files (e.g. passwords in a yaml) are readable by the token holder. Mitigate with --docs-only and pre-publish review.
  • Full-mode scripts can phone home: the sandbox blocks same-origin access but not outbound requests. Use safe render for untrusted HTML.
  • Token = everything: with a single token, leakage equals document-set leakage. Mitigate with instant token rotate; the audit log reveals abnormal access.
  • Fail-open rate limiting: the global failure cap blocks only the offending source key, prioritising owner availability (no self-lockout). Brute force is infeasible over a 256-bit token space.
  • Symlink TOCTOU inside published roots: a concurrent modification between check and read could slip past containment. Inside the trust boundary (editing the root requires local access already); not further mitigated.
