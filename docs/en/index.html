Research Report: Workspace Docs on Your Phone

The missing piece of a document-driven workflow: read-only Markdown and HTML documents from any workspace, on your phone, without widening the PC's attack surface. This page records the requirements, the survey of existing tools, and the final selection.

Researched 2026-10-05 · Evidence: GitHub API, Cloudflare docs, OWASP Cheat Sheet (sources listed at the bottom)

1. Requirements

IDRequirementWhy
R1 Explicit grantOnly explicitly authorised directories are visible on the phoneThe tunnel must never become a backdoor to the whole PC filesystem
R2 Read-onlyNo editing on the phoneDocument changes continue to go through your editor or coding agent on the PC; the phone only consumes
R3 RenderingMarkdown and HTML rendering — HTML at minimumDocuments must be readable, not downloaded as source
R4 TokenToken required; no anonymous accessA public URL must not mean public content
R5 SafetyAs secure as possible without hurting daily useWhatever else already runs on the PC and its tunnel (existing services, remote-control channels) stays untouched

Implicit constraints from the usage scenario: open on a phone at any time (no site build step), single user (no account system), and unreliable CDN access from some networks — so static assets must ship with the repo.

2. Method

Look for existing wheels first; only build what is missing. Every candidate was checked for three things:

  • Capability fit — does it satisfy R1–R5 as-is, or does it need surgery?
  • Popularity — GitHub stars (read via the GitHub API on 2026-10-05);
  • Activity — last commit date and whether the repository is archived (archived = undependable).

3. Options considered

Option A: extend an existing relay service

If the tunnel already carries a relay (file sync, remote control, an agent command channel), add a read-only /docs endpoint and a phone page to it, reusing its tunnel, token and audit log. Cheapest to deploy — but it grows the attack surface of that service itself: any flaw in document parsing or path handling sits right next to the interface that service exposes to the outside world. That contradicts R5, so it was rejected.

Option B: off-the-shelf file servers

ProjectStarsLast commitFit
sigoden/dufs 10,8352026-06 Feature-rich (search, upload, WebDAV), usable read-only — but no Markdown rendering, Basic/Digest auth instead of Bearer tokens, and a single root per instance, so no per-workspace publishing. Its write features must be locked down even when unused.
svenstaro/miniserve 7,8892026-10 Stable and actively maintained read-only static server — but no Markdown rendering, HTTP Basic auth (password prompt on every visit; poor phone experience), and again a single root.
filebrowser/filebrowser 35,927archived Repository archived An editor-equipped drive — violates R2 — and unmaintained. Excluded.

File servers solve "move bytes", not "render" or "publish on demand". Adding a rendering layer still leaves the authorisation model to write — at which point composing rendering libraries directly is the simpler path.

Option C: off-the-shelf documentation tools

ProjectStarsLast commitFit
docsifyjs/docsify 31,5442026-10 Client-side Markdown site with great rendering — but its model is "one site, one index.html + sidebar". No multi-root, on-demand publishing and no auth. Watching an arbitrary workspace would mean standing up and syncing a site per workspace, which defeats "open it anytime".
squidfunk/mkdocs-material 27,5402026-10 Best-in-class static docs sites — but it needs a build step: a document the agent just wrote requires a rebuild before you can read it. Great for published docs, wrong for working docs.
dullage/flatnotes 3,2372026-08 Self-hosted Markdown notes with a built-in editor (violates R2) and a single-library model; cannot browse several workspace directories.

Option D: a thin read-only gateway + battle-tested rendering stack (chosen)

Only the unavoidable glue is written by hand: explicit publish grants, token auth, a path sandbox, a read-only API. Rendering is delegated to mature open-source wheels, vendored into the repository:

WheelStarsLast commitLicenseRole
markedjs/marked v18.0.14 37,2232026-10MIT Markdown → HTML in the browser, zero dependencies
cure53/DOMPurify 3.4.16 17,4392026-10Apache-2.0 HTML/XSS sanitisation. The OWASP XSS Prevention Cheat Sheet recommends sanitising user-authored HTML and names DOMPurify
highlightjs/highlight.js 11.12.0 25,0032026-09BSD-3-Clause Code-block syntax highlighting

The server uses only the Python 3 standard library — the target machine (your PC) already has Python, installation is frictionless, and there is no runtime supply chain to speak of. The phone viewer is dependency-free TypeScript compiled to plain JavaScript.

Conclusion: Option D. The gateway is custom because no existing product combines "multi-root, publish on demand + Bearer token + read-only + rendering" — while the genuinely risky and difficult parts (Markdown parsing, XSS sanitisation, syntax highlighting) are all left to libraries with 17k–37k stars that are actively maintained.

4. Infrastructure checks

  • One tunnel, many services: a locally managed Cloudflare Tunnel maps hostnames to local services via ingress rules. Adding docs.yourdomain → 127.0.0.1:8380 leaves the relay's rules untouched — zero change to the control plane (source: Cloudflare "Published applications / configuration file").
  • Free tier: publishing an application through a tunnel needs no paid plan; only Cloudflare Access (the optional second layer) needs Access seats.
  • HTTPS: the tunnel edge terminates TLS; the service itself binds 127.0.0.1 only.

6. Known trade-offs

  • No full-text search: the phone is for reading; filename filtering covers the basic case, and search can be added later.
  • No multi-user model: one person, one token; revocation is global, and the simple model is the safer one.
  • Full-fidelity HTML scripts are constrained: the default render is the sanitised one; interactive HTML with scripts goes through a sandboxed iframe (see Design). The browser sandbox limits those scripts — the price of protecting the token.
  • Vendored assets instead of CDN: about 200 KB extra in the repo, in exchange for the phone working on weak networks and no CDN-side supply-chain risk.
